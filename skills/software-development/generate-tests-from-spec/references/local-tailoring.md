# ローカル差分

公開版のSpec Modeでケースを設計し、既存のPython環境でpytestを作成・実行する。

## 入力と確認

- 要求仕様、対象コード、既存テスト、テスト設定を確認する。対象機能と依存箇所を絞り、リスクに応じて範囲を広げる。
- 結果・範囲・安全性・期待結果に影響する不明点は、依存する作業の前に質問する。判明済み事項と必要な回答を示し、回答後は途中から再開する。確認済み仕様で決まる詳細は進める。
- 推測や無断の代替で期待結果を決めない。曖昧な仕様を現行コードの挙動だけで確定しない。仕様で認めたnullやunknownは、その意味を保つ。

## ケース設計

- 既存ケース・IDを再利用し、要求→ケース→pytestの対応を記録する。正常系、異常系、境界値、回帰、副作用を対象にする。
- 既存の文書配置とケース管理方式を使う。対応表は必要な範囲に絞り、同じ内容の文書を増やさない。
- 原文の`code-forge:tdd`への引き渡しは、このSkill内でのpytest実装・実行に置き換える。
- 原文の`sf-scan`、`sf-trace`、`sf-verify-doc`は導入しない。既存のファイル検索・コード読解、要求とケースの対応表、同梱チェックリストで確認する。
- 原文中の`@../shared/*`は`references/upstream-shared/*`を読む。上流のスクリプト説明は参考資料とし、この環境で実在するツールだけを実行する。
- 補助資料中の`skills/test-cases-generation/references/*`は、このSkillの`references/*`へ対応する。`spec-forge:*`の文書整合・伝播操作は、既存文書と参照元を照合し、依頼された範囲の修正へ置き換える。

## pytest実装と実行

- 既存のPython、fixture、設定、テスト配置を使う。既存テストを拡張し、依存関係の追加が必要なら確認する。
- 外部サービスは模擬化する。ファイル・SQLiteの実操作は、一時ディレクトリと隔離した試験用データに限定する。
- dry-runと模擬applyを分け、失敗時の正常データ保持、重複防止、再実行を必要な範囲で検証する。稼働外部サービスや本番データを変更しない。
- 関連テストを実行し、実際の収集数・成功・失敗・skipを記録する。既存挙動に対するテストは初回から成功する場合もある。失敗は原因と仕様との関係を調べる。
- 製品コードや正式仕様の変更は、依頼された範囲で行う。テスト整備の依頼だけで製品の挙動を変更しない。

## 報告

要求との対応、模擬化した依存、未実行箇所、残る制約を示す。実装とテストが同じ誤読に基づく可能性も確認する。形式チェック、カバレッジ、挙動検証の結果を分ける。
