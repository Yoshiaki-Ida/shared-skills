# ローカル差分

公開版のDocumentation modeを使い、現行実装から要求仕様を起こす。

## 対象と確認

- 対象リポジトリ・版・出力先を確認する。版の指定がなければ現在の作業ツリーを対象とし、未コミット変更を含むことを記録する。
- Modernization mode、移行、コード変更、Copilot指示ファイルの生成は、依頼された場合だけ行う。
- 結果・範囲・安全性・成果物に影響する不明点は、依存する作業の前に質問する。判明済み事項と必要な回答を示し、回答後は途中から再開する。確認済み入力で決まる詳細は進める。
- 推測や無断の代替で要求を補わない。根拠がある項目を`[確認済み]`、推論を`[推定]`として区別する。未実装の要望は現行仕様へ混ぜない。

## 根拠の収集

- コード、README、UI、設定例、起動スクリプト、テストを照合する。コードの読み取りで確認した事実と、実行で確認した結果を分ける。
- 仕様に使う根拠はファイル・関数・設定項目へ対応付ける。文書と実装の不一致、動的に確認できなかった挙動を残す。
- 実トークン、個人メール、内部接続先、実チケット本文などを仕様書へ転記しない。設定名と匿名化した例を使う。

## 要求仕様の出力項目

1. 目的、利用者、実行環境。
2. 機能、入口、入力、処理、出力、副作用、保存先。
3. モジュール、公開API、データ型、Web API。
4. 設定・環境変数、既定値、必須条件、欠損値と0の意味。
5. フロー、状態、失敗、再実行、中断、復旧。
6. UI、エラー表示、前後工程との接続。
7. 文書との不一致、根拠、制約、未検証事項。

既存文書の構成と出力先を再利用する。既存の正式仕様を更新する際は、適用される承認条件を確認し、差分と根拠を提示する。`continuous-spec-reconciliation`が利用可能ならその手順を使う。文書化から製品の挙動変更へ範囲を広げない。
