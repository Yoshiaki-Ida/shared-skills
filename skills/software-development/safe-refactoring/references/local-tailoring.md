# ローカル差分

公開版の小さな変更と検証の手順を、既存Python PoCの保守に適用する。

## 範囲と確認

- 対象は構造・命名・重複・パス・importの改善。UI操作、API、設定、入出力ファイル、欠損値の意味を保つ。機能追加や契約変更が必要なら、影響を示して変更範囲を確認する。
- 結果・範囲・安全性・成果物に影響する不明点は、依存する変更の前に質問する。判明済み事項と必要な回答を示し、回答後は途中から再開する。確認済み仕様で決まる詳細は進める。
- 推測、無断の代替、フォールバック、対象拡大で不明点を埋めない。仕様で定義されたnullやunknownは、その意味を保って扱う。

## 作業と検証

- 現在の未コミット変更と既存テストを確認し、変更前の結果を記録する。失敗があれば対象との関係を調べる。元からある失敗と今回の回帰を分ける。
- 各変更を一つの目的に絞る。既存の関数・クラス・表現を再利用し、共通化による挙動差を確認する。行数やパターンのチェック項目は調査の目安に使う。
- テストが不足する箇所は必要な回帰を先に用意する。既存コードの一括削除や広い置換を、テスト不足の解決手段にしない。
- 変更後は関連テストを実行する。未解決の懸念や波及がある場合は範囲を広げる。既存のPython環境・テスト設定を使い、導入や環境変更が必要なら確認する。
- import、プロジェクトルートを基準としたパス、BAT/PowerShell、テンプレート、環境変数・設定、保存先、UI/APIの接続を確認する。外部サービスは模擬データで検証する。

## Gitと復旧

- 原文のコミット・ブランチ作成は、ユーザーが依頼した範囲で行う。変更前後の差分と検証結果を残し、無関係な変更を保持する。
- 失敗時は自分の変更範囲と復元元を特定して戻す。未コミット変更があるファイルへの無条件な`git restore`、`reset --hard`、`git clean`は行わない。
- 既存仕様と実装の差分、前後工程の接続を確認する。正式仕様の変更が必要なら案を提示し、承認後に反映する。`continuous-spec-reconciliation`が利用可能ならその手順を使う。最終報告に変更理由、関連テスト、起動・接続確認、残る制約を記録する。実行していない検証は未検証とする。
